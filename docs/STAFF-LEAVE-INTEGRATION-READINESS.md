# บันทึกตรวจความพร้อมเชื่อมระบบบริหารการลา (Integration Readiness)

สถานะ: ตรวจสอบแบบอ่านอย่างเดียว — ยังไม่ใช่ Production implementation  
Repository: `wbns-edoc/wbns-edoc.github.io`  
สาขางาน: `feat/staff-leave-management-design`

## 1. ผลตรวจ schema Production

ตรวจรายการตารางใน schema `public` ผ่าน Supabase แบบอ่านอย่างเดียว พบโครงสร้างเดิมที่ควรนำมาเชื่อมต่อ:
- `profiles`: ข้อมูลผู้ใช้/บุคลากร เช่น `id`, `employee_code`, `full_name`, `email`, `department_id`, `is_active`
- `departments`: หน่วยงานแบบมี `parent_id`, `code`, `name`, `is_active`
- `roles`, `user_roles`, `permissions`, `role_permissions`: บทบาทและสิทธิ์ส่วนกลาง
- `user_departments`, `user_department_roles`, `department_role_permissions`: การเป็นสมาชิกหลายกลุ่มงานและสิทธิ์เฉพาะกลุ่มงาน
- `audit_logs`: ระบบบันทึกเหตุการณ์ที่มีอยู่แล้ว ควรตรวจรูปแบบก่อนตัดสินใจว่าจะเพิ่ม event table เฉพาะระบบลาหรือไม่

ตารางที่ตรวจพบข้างต้นเปิดใช้ RLS อยู่ การตรวจนี้ไม่ใช่การยืนยันว่า policy ทุกตารางปลอดภัยครบถ้วน และไม่ใช่การทดสอบ end-to-end

## 2. ผลตรวจช่องว่าง

- ยังไม่พบตารางระบบลาในรายการ schema ที่ตรวจได้ จึงต้องถือว่าระบบลาเป็นฟีเจอร์ใหม่จนกว่าจะตรวจสอบครบถ้วน
- ประเภทบุคลากรต้องแยกจาก role/department และใช้เป็นข้อมูลประกอบรายงานเท่านั้น ตามมติของโรงเรียนให้บุคลากรทุกประเภทใช้กฎการลาชุดเดียวกัน ห้ามใช้ประเภทการจ้างเลือกสิทธิหรือสูตรคำนวณที่ต่างกัน
- อย่าถือว่า System Admin มีสิทธิ์อ่านเหตุผลการลาหรือเอกสารแนบที่อ่อนไหวโดยอัตโนมัติ
- การคำนวณวันลาและยอดคงเหลือต้องปิดไว้จนกฎ school-wide ปฏิทินวันทำการ ประวัติอายุงาน และข้อมูลสิทธิที่จำเป็นได้รับการตรวจสอบและอนุมัติ
- ห้ามสมมติว่าหนังสือ ว 14/2568 ใช้กับพนักงานราชการหรือครูอัตราจ้างทุกกรณี ต้องยืนยันแหล่งข้อกำหนดแยกตามกลุ่ม

## 3. ลำดับงานที่ปลอดภัย

1. ตรวจ schema, constraints, triggers, RLS policies และ helper RPC ที่มีอยู่ให้ครบ โดยอ่านอย่างเดียว
2. ทำตาราง mapping ระหว่าง `profiles` / หน่วยงาน / membership กับข้อมูลผู้ยื่นและผู้อนุมัติ
3. ทำ policy matrix แบบ school-wide แยกตามประเภทการลาและผู้มีอำนาจอนุมัติ พร้อมแหล่งอ้างอิงและวันที่มีผล โดยไม่แยกสิทธิ/สูตรคำนวณตามประเภทบุคลากร
4. สร้าง migration แบบ additive เฉพาะบน feature branch หลังยืนยันชื่อ/ชนิดข้อมูลและรูปแบบ RLS ที่เหมาะสม
5. เพิ่ม tests สำหรับผู้ใช้เห็นเฉพาะคำขอตนเอง, ผู้อนุมัติเห็นเฉพาะขอบเขต, ป้องกันอนุมัติตนเอง, ป้องกันการแก้ประวัติ action, ไฟล์แนบส่วนตัว และการลง ledger ซ้ำ
6. ทดสอบบน local/staging ที่แยกจาก Production ก่อนเสนอ PR และ deploy

## 4. เกณฑ์ห้ามข้าม

- ไม่มีการรัน migration บน Production จากบันทึกตรวจนี้
- ไม่มีการ seed กฎสิทธิ์วันลาแบบเดาตัวเลข
- ไม่มี public URL สำหรับไฟล์แนบที่มีข้อมูลส่วนบุคคล
- ทุกการเปลี่ยนแปลงสิทธิ์และ workflow ต้องตรวจฝั่งฐานข้อมูล/server ไม่พึ่งการซ่อนปุ่มใน UI
- หากยังไม่มี staging ที่แยกจริง ต้องสร้าง/ยืนยันสภาพแวดล้อมทดสอบก่อน deploy

## 5. ข้อจำกัดของผลตรวจ

นี่คือผลตรวจแบบอ่านอย่างเดียวของรายการตารางและคอลัมน์ที่เครื่องมือส่งคืน ไม่ได้ยืนยัน policy definition ทั้งหมด, trigger/function source ทั้งหมด, ความครบถ้วนของคู่มือ PDF ทั้ง 33 หน้า หรือการทดสอบระบบจริง
