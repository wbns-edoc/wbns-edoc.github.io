# แบบจำลองข้อมูลระบบบริหารการลาเจ้าหน้าที่ — ฉบับออกแบบ

สถานะ: **เอกสารออกแบบเท่านั้น (Draft / Not Production)**  
สาขา: `feat/staff-leave-management-design`  
ขอบเขต: ใช้ประกอบการออกแบบระบบการลาของบุคลากรโรงเรียนวัดบึงน้ำใส โดยยังไม่สร้าง/แก้ไขตารางจริง ไม่รัน migration และไม่เปิดใช้การคำนวณสิทธิ์ลาใน Production

## 1. หลักการออกแบบ

1. รองรับประเภทบุคลากรหลายกลุ่ม เช่น ข้าราชการครูและบุคลากรทางการศึกษา, พนักงานราชการ, ครูอัตราจ้าง/ลูกจ้าง และประเภทเพิ่มเติมที่โรงเรียนกำหนดได้
2. **อย่าสรุปว่ากฎของบุคลากรทุกประเภทเหมือนกัน** นโยบายแต่ละชุดต้องผูกกับประเภทบุคลากรและช่วงวันที่มีผล
3. แยก “คำขอลา”, “การอนุมัติ”, “เอกสารแนบ”, “ยอดสิทธิ/รายการเคลื่อนไหว” และ “หลักฐานแหล่งกฎ” ออกจากกัน
4. เก็บประวัติการเปลี่ยนแปลงสำคัญแบบตรวจสอบย้อนหลังได้ ไม่เขียนทับประวัติการอนุมัติเดิม
5. การคำนวณวันลา/ยอดคงเหลือเปิดใช้ได้ต่อเมื่อกฎที่เกี่ยวข้องได้รับการตรวจสอบจากแหล่งทางการและผู้รับผิดชอบงานบุคคลอนุมัติแล้ว
6. แบบจำลองนี้เป็นข้อเสนอเชิงสถาปัตยกรรม ต้องตรวจเทียบ schema, auth/RLS และรูปแบบโค้ดที่มีอยู่ใน repository ก่อนออก migration

## 2. องค์ประกอบข้อมูลที่เสนอ

| ตาราง/เอนทิตี (ชื่อเสนอ) | จุดประสงค์และข้อมูลหลัก |
|---|---|
| `personnel_categories` | รหัส/ชื่อประเภทบุคลากร, สถานะใช้งาน, วันที่มีผล |
| `leave_types` | รหัส/ชื่อประเภทการลา, คำอธิบาย, สถานะใช้งาน |
| `leave_policy_versions` | รุ่นนโยบายต่อคู่ประเภทบุคลากร + ประเภทการลา, วันเริ่ม/สิ้นสุด, สถานะ Draft/Review/Approved/Retired, ผู้อนุมัติและเวลาที่อนุมัติ |
| `leave_policy_rules` | รายละเอียดกฎที่ผ่านการยืนยัน เช่น วิธีนับวัน, เงื่อนไขแจ้งล่วงหน้า, เอกสารประกอบ, ข้อจำกัด/ยอดสะสม และการตั้งค่าที่มีแหล่งอ้างอิง ห้ามตั้งค่าตัวเลขที่ยังไม่ยืนยัน |
| `leave_policy_sources` | ชื่อเอกสาร/หน่วยงาน, เลขที่หนังสือ, วันที่, URL/ที่เก็บไฟล์, เลขหน้า, วันที่ตรวจสอบ, ผู้ตรวจ และหมายเหตุเรื่องการยกเลิก/แทนที่ |
| `leave_requests` | ผู้ยื่น, ประเภทบุคลากร ณ วันที่ยื่น, ประเภทลา, วันเริ่ม/สิ้นสุด, เหตุผลที่จำเป็น, สถานะ, ผู้แทนงาน/ผู้ติดต่อ และ timestamps |
| `leave_attachments` | คำขอที่เกี่ยวข้อง, object key ใน private storage, ชื่อไฟล์, MIME, ขนาด, checksum, ผู้อัปโหลดและเวลา; ไม่เก็บ public URL ที่เปิดได้โดยไม่ตรวจสิทธิ์ |
| `leave_approval_steps` | ขั้นตอนอนุมัติ, ลำดับ, ผู้มีอำนาจ/ผู้รับมอบหมาย, หลักเกณฑ์การกำหนดผู้อนุมัติและสถานะขั้นตอน |
| `leave_approval_actions` | บันทึก append-only ของการส่งต่อ/อนุมัติ/ไม่อนุมัติ/ส่งกลับ/ยกเลิก พร้อมผู้กระทำ เวลา ความเห็น และขั้นตอนที่เกี่ยวข้อง |
| `leave_balance_ledger` | รายการเพิ่ม/หัก/ปรับยอดที่อ้างอิงคำขอหรือการปรับที่ได้รับอนุมัติ; ไม่ใช้ยอดคงเหลือที่แก้ไขตรงโดยไม่มี ledger |
| `leave_audit_events` | ประวัติการแก้ไขสถานะ/ข้อมูลสำคัญและเหตุผล โดยจำกัดสิทธิ์อ่านและไม่บันทึกความลับหรือเนื้อหาอ่อนไหวเกินจำเป็น |

ชื่อตารางเป็นข้อเสนอเท่านั้น ต้องตรวจว่าระบบมีตาราง/คอลัมน์ที่ทำหน้าที่เดียวกันอยู่แล้วหรือไม่ก่อนสร้างสิ่งใหม่

## 3. ความสัมพันธ์หลัก

- บุคลากรหนึ่งคนยื่นคำขอได้หลายรายการ; คำขอแต่ละรายการมีผู้ยื่นหนึ่งคนและอ้างอิงประเภทการลา
- นโยบายหนึ่งรุ่นผูกกับประเภทบุคลากรหนึ่งประเภทและประเภทการลาหนึ่งประเภท และอาจอ้างอิงแหล่งกฎหลายรายการ
- คำขอมีเอกสารแนบหลายไฟล์และขั้นตอนอนุมัติหลายขั้น
- ขั้นตอนอนุมัติหนึ่งขั้นมี action ได้หลายรายการเพื่อเก็บประวัติส่งกลับ/ดำเนินการใหม่
- รายการ ledger ต้องอ้างอิงเหตุการณ์ต้นทางที่ตรวจสอบได้ และป้องกันการลงรายการซ้ำ
- ต้องกำหนดว่าประเภทบุคลากรและนโยบายใดใช้ ณ วันที่ยื่น/วันที่ลาอย่างชัดเจน ห้ามให้การแก้ประเภทบุคลากรปัจจุบันเปลี่ยนประวัติคำขอเก่าโดยเงียบ ๆ

## 4. สถานะคำขอที่เสนอ

`draft → submitted → pending_approval → approved | rejected | returned`

สถานะเสริมที่ต้องกำหนดความหมายและสิทธิ์ก่อนใช้จริง: `cancel_requested`, `cancelled`, `withdrawn`, `completed`.

ทุก transition ต้องตรวจฝั่งฐานข้อมูลหรือฝั่ง server ที่เชื่อถือได้ ไม่พึ่งเพียงการซ่อนปุ่มใน UI การอนุมัติ/ปฏิเสธต้องบันทึกผู้กระทำ เวลา และเหตุผลตามความเหมาะสม ห้ามผู้ยื่นอนุมัติคำขอตนเอง เว้นแต่ระเบียบที่ผ่านการอนุมัติและการควบคุมแยกหน้าที่ระบุเป็นอย่างอื่นอย่างชัดเจน

## 5. สิทธิ์เข้าถึงและข้อมูลส่วนบุคคล

- ผู้ยื่นเห็นคำขอของตนเองและสถานะที่จำเป็น
- ผู้อนุมัติเห็นเฉพาะคำขอในขอบเขตอำนาจ/การมอบหมายที่ยืนยันแล้ว
- เจ้าหน้าที่งานบุคคลเห็นข้อมูลที่จำเป็นต่อหน้าที่ตามบทบาทที่อนุมัติ
- System Admin ไม่ควรได้รับสิทธิ์เปิดดูรายละเอียดเหตุผลหรือเอกสารอ่อนไหวโดยอัตโนมัติเพียงเพราะดูแลระบบ; ให้แยกสิทธิ์ทางเทคนิคออกจากสิทธิ์เข้าถึงข้อมูลบุคคล และบันทึกการเข้าถึงที่มีความเสี่ยง
- เปิดใช้ RLS สำหรับตารางที่มีข้อมูลบุคลากร; ไฟล์อยู่ใน private bucket/folder และดาวน์โหลดผ่านการตรวจสิทธิ์
- หลีกเลี่ยงการบันทึกเลขบัตรประชาชน/ข้อมูลสุขภาพ/เหตุผลส่วนตัวซ้ำใน audit log; ใช้การปกปิดข้อมูลและ retention policy ที่โรงเรียนอนุมัติ
- ตรวจความเป็นเจ้าของไฟล์, ขนาด, MIME และสิทธิ์การดาวน์โหลดฝั่ง server

## 6. การกำหนดผู้อนุมัติ

อย่าฝังชื่อบุคคลหรือสายอนุมัติไว้ในโค้ดถาวร ให้เก็บเป็น configuration ที่มี effective dates และมีผู้อนุมัติการเปลี่ยนแปลง โดยอ้างอิงระเบียบที่ใช้กับประเภทบุคลากรนั้น ๆ

สำหรับข้าราชการครูและบุคลากรทางการศึกษา ต้องตรวจหนังสือ ก.ค.ศ. ว 14/2568 เรื่องผู้มีอำนาจพิจารณาหรืออนุญาตการลา (ประกาศ 3 เมษายน 2568) และตรวจเอกสารฉบับเต็ม/ข้อกำหนดที่เกี่ยวข้องก่อนแปลงเป็น workflow ส่วนบุคลากรประเภทอื่นต้องตรวจฐานกฎหมาย สัญญาจ้าง หรือแนวปฏิบัติที่ใช้กับกลุ่มนั้นแยกต่างหาก ห้ามอนุมานจาก ว 14/2568 ว่าครอบคลุมทุกประเภทบุคลากร

## 7. เกณฑ์ก่อนพัฒนา schema/migration

- [ ] ตรวจ schema ปัจจุบันและตารางบุคลากร/โปรไฟล์/หน่วยงานที่มีอยู่
- [ ] ตรวจ auth provider, RLS policies, helper functions และรูปแบบ audit ที่โครงการใช้
- [ ] ตรวจเอกสารกฎลาครบทั้ง 11 ประเภทและบันทึกเลขหน้าเอกสารต้นฉบับ
- [ ] ผู้รับผิดชอบงานบุคคลยืนยันกฎแยกตามประเภทบุคลากรและช่วงวันที่มีผล
- [ ] ผู้มีอำนาจอนุมัติยืนยันสายอนุมัติและกรณีมอบหมาย/ผลประโยชน์ทับซ้อน
- [ ] ออกแบบ tests สำหรับการเข้าถึงข้ามผู้ใช้, ข้ามประเภทบุคลากร, การอนุมัติตนเอง, การลง ledger ซ้ำ และไฟล์แนบส่วนตัว
- [ ] ทำ migration แบบ additive พร้อม rollback/backup plan และทดสอบใน environment ที่ไม่ใช่ Production ก่อน
- [ ] ไม่มีการ deploy หรือเปิดใช้การคำนวณสิทธิ์จนกว่าจะผ่านการตรวจและอนุมัติ

## 8. แหล่งอ้างอิงและข้อจำกัด

- คู่มือการปฏิบัติงานเกี่ยวกับการลาประเภทต่าง ๆ ของข้าราชการ, ศูนย์เทคโนโลยีสารสนเทศและการสื่อสาร สำนักงานปลัดกระทรวงศึกษาธิการ — มีหัวข้อการลา 11 ประเภทและแบบฟอร์มในภาคผนวก; ต้องตรวจถอดข้อความจาก PDF ต้นฉบับครบถ้วนก่อนใช้ออกกฎระบบ
- ก.ค.ศ. ว 14/2568 ลงวันที่ 3 เมษายน 2568: https://otepc.go.th/th/content_page/item/5332-14-2568.html — ใช้ตรวจอำนาจพิจารณา/อนุญาตการลาสำหรับกลุ่มที่หนังสือครอบคลุม
- สถานะของเอกสารนี้ไม่ใช่การยืนยันสิทธิการลาตามกฎหมาย และไม่ใช่คำสั่งอนุมัติใช้งาน Production
